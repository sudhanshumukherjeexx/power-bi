# SQL validation

Every SQL example in the project (worked solutions, Toolkit guides, evidence files) declares a **dialect**, and each is checked in one or more ways. Nothing is labelled portable unless it has actually been run on both engines.

## Dialects

| Dialect | Meaning | How to mark it |
|---|---|---|
| `portable` | Runs unchanged on SQLite **and** SQL Server | solutions: `"dialect": "portable"`; guides: ` ```sql portable ` |
| `sqlite` | Uses SQLite functions (`strftime`, `julianday`…). The note says what to use on SQL Server | `"dialect": "sqlite"` / ` ```sql sqlite ` |
| `tsql` | SQL Server only (`MERGE`, `[brackets]`, index DDL, `@parameters`) | `"dialect": "tsql"` / ` ```sql tsql ` |

Write portable SQL for anything a learner might run on either engine. Quote identifiers that are reserved words in either engine: `"LineNo"` in portable code (`LINENO` is reserved in T-SQL) and `[LineNo]` in T-SQL.

## Validation levels

| Level | What it proves | Where it runs |
|---|---|---|
| **executed** | The query runs on SQLite against the generated data, and its result equals the expected rows in the solution (which are filled from the same data) | `tests/sql.test.js`, every push (blocks the deploy) |
| **parsed** | The block parses in its dialect with SQLFluff. Portable blocks are parsed as both SQLite and T-SQL | CI job `sql`, every push (blocks the deploy) |
| **sql-server** | The query runs on SQL Server 2022 (CU pinned). Every executed portable block returns the **same rows as on SQLite**. The T-SQL `MERGE` is idempotent and loads the expected rows, and the T-SQL rewrite returns as many rows as its portable version | `.github/workflows/sql-server.yml` (on SQL changes, monthly, on demand) |

Run them locally:

```bash
npm test                                         # executed (SQLite)
pip install -r requirements-dev.txt              # once
node tools/sql-catalog.js --extract .sql-lint
sqlfluff parse --dialect tsql .sql-lint/tsql && sqlfluff parse --dialect sqlite .sql-lint/sqlite
docker run -d --name pbi-sql -e ACCEPT_EULA=Y -e MSSQL_SA_PASSWORD='Your_Local_Pw1!' -p 14333:1433 mcr.microsoft.com/mssql/server:2022-CU27-ubuntu-22.04
MSSQL_SA_PASSWORD='Your_Local_Pw1!' SQLSERVER_PORT=14333 node tools/sqlserver-check.js
```

## What the first run found (October 2026)

Adding these levels found four real bugs in examples that were already marked as checked:

- **`LineNo` is a reserved word in T-SQL.** Every portable query and T-SQL example that used it unquoted (25 lines, including the `MERGE` and the slow-query evidence file) failed on SQL Server with *Incorrect syntax near the keyword 'LineNo'*. They now quote it.
- **`CREATE TABLE … AS SELECT`** (the SCD type 2 solution) is not SQL Server syntax. It now uses an explicit `CREATE TABLE` followed by `WITH … INSERT`.
- **`SUM(CASE WHEN EXISTS (…))`** (early-arriving facts) can't be aggregated in SQL Server. It is now a `LEFT JOIN` to the distinct keys. The answer is the same on both engines.
- An untagged block (composite models) was given its dialect.
